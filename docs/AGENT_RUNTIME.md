# Agent runtime

State transitions: `idle → requesting → validating → executing → requesting`; final actions enter `verifying → completed`. Every uncaught failure ends in `failed` or `timed_out`. Each transition carries a monotonic elapsed timestamp and is emitted in the result and JSONL logs.

The full-context strategy stores the original task, tool descriptions, accepted actions, observations, and corrective errors. Each observation includes its stable run-local ID, tool name, validated arguments, structured result, and execution latency. State transitions remain in the result event history, and raw inference responses remain in the result for debugging. Tool contents are labeled as untrusted data, and no unrestricted shell or dynamic code execution handler exists.

The controller constrains allowed action phases using those explicit task cues: final actions are unavailable until required evidence exists; after a required query succeeds, a required report must be written before further actions. Ranking cues require nonempty CSV sort keys and a limit; filter cues such as “below” require nonempty CSV filters. Report source IDs are constrained to actual successful observations. This is a fixed baseline workflow guard, not an optimization experiment or a general natural-language planner. The model still selects query arguments, report sources, title, and filename. Tasks requesting multiple distinct reports or complex conditional workflows may need a richer explicit task contract in future.

Where file references are available in the task or successful listings, generated file arguments are constrained to those paths by file type. Unknown paths are not silently rewritten. Final evidence is constrained to the successful observation list (up to 32 IDs), so the model cannot omit a verified report or invent observation IDs. These constraints preserve provenance; they do not prove that the query implements the user's intent.

Each inference request consumes a step, including invalid requests. Invalid output corrections also share a separate run-wide retry budget. Repeating the same canonical tool-name/arguments pair is rejected after the configured identical-action limit. Tools run under the earlier of the task deadline and tool deadline. The HTTP transport enforces remaining time and bounded response bytes.

A tool error is recorded and exposed to the model for recovery. The agent can continue with a different valid call. Maximum steps, exhausted correction budget, backend failure, context overflow, missing evidence, invalid final response, and timeout all produce a non-success result and a nonzero exit code.

Successful final actions require a nonempty answer and successful observation IDs, including a data read/query observation. Conservative word cues for explicit CSV/SQLite ranking/filtering and report creation additionally require a cited query and/or verified report observation. These guards are heuristic, not a semantic task parser. Premature final actions receive corrective feedback within the same bounded correction budget. Reports are checked at creation. This generic verifier cannot prove arbitrary natural-language task satisfaction: a model could cite valid evidence while giving an incorrect interpretation. The benchmark harness independently checks exact task-specific query rows and report contents, and records `verified_success` separately from the agent's completion flag. Applications needing stronger acceptance must supply deterministic task-specific checks.

Tools use conservative fixed limits: 2 MiB CSV files, 20,000 merged rows, 128 columns, 16 KiB fields, 16 input paths, 200 returned rows, 48 KiB observations, 24,000-byte text files, 16 MiB SQLite snapshots, and 256 KiB reports. The registry rejects oversized observations with an instruction to narrow the query. CSV numeric values use finite double precision; finite numeric-text filter values normalize to numbers when the data column is numeric. Empty/nonnumeric cells are counted during inspection and rejected by numeric aggregates. CSV merges require identical ordered headers. Sort keys are applied lexicographically in the supplied order. `limit` selects top results and exposes truncation. Aggregation supports count/sum/mean/min/max, optionally by one group column. Multi-objective optimization is not implied: FPS plus size examples use explicit FPS-first ranking and size as a tie breaker.

SQLite accepts one read-only prepared statement with an allowlist authorizer. Writes, PRAGMAs, ATTACH, unknown SQL functions, extensions, BLOB results, duplicate output column names, and multiple statements are rejected. CTEs are permitted. A progress handler enforces the deadline and a ten-million-VM-instruction upper budget; results, expression depth, byte lengths, and statement complexity are bounded. Temporary operations stay in memory. WAL databases must first be checkpointed and converted to DELETE journal mode by the database owner; tools never modify the source database.
